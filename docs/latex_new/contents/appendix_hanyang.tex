\chapter{Android Client Evaluation Reproducibility}
\label{app:android-evaluation}

\section{Environment and Protocol}

The Android client measurements use an Android~14/API~34 Google APIs
x86\_64 emulator with a Pixel~6 device profile. The device profile, display
configuration, Android image, WebView package, host CPU affinity, application
build, and measurement code remain fixed within the resource experiment. The
seed-initialization and event-synchronization experiments connect the emulator
to disposable local backend services through the emulator host-network route.
Authentication values are supplied at run time and excluded from the retained
artifacts.

The resource protocol starts one wiped-data, cold-booted emulator process for
each session. Within a session, the startup benchmark seeds a deterministic
five-paper briefing into the production Room schema. Each launch scenario
records six native Macrobenchmark observations. The first observation remains
in the raw Android output as the protocol warm-up, while observations two to
six form the five analyzed values. The graph experiment uses deterministic
payloads with 1, 12, 25, and 50 nodes. Node count increases in the first block
and decreases in the second. For each node count, the protocol retains five
new-and-reused WebView pairs after one complete warm-up pair.
For \(N=1,12,25,50\), the payload generator constructs respectively
0, 16, 36, and 73 directed edges. Each node after the first points to its
predecessor, and every even-indexed node from index two adds one edge to the
node seven positions ahead modulo \(N\). Node and edge identities and topology
remain fixed across sessions; only the WebView state and emulator resource
allocation vary.

\subsection{Resource-Controlled Protocol}

The resource-controlled experiment uses the same Android~14/API~34 Google
APIs x86\_64 image and Pixel~6 profile in all sessions.
The four configurations combine two or four virtual processor cores with
2{,}048 or 6{,}144~MiB of emulator RAM.
The first block uses the order 2-core/2-GiB, 2-core/6-GiB,
4-core/6-GiB, and 4-core/2-GiB. The second block reverses this order. The
design contains two sessions per configuration and eight sessions in total.

The analysis unit is one emulator session. Five retained observations first
form one median for each metric within a session. Both session medians in a
resource condition are then reported together with their median, minimum,
maximum, and range. Within each block, the CPU comparison measures the
percentage change from two to four cores at each RAM level, while the RAM
comparison measures the change from 2 to 6~GiB at each CPU level. More
formally, let \(L_{c,r}\) denote a block's session-median latency with \(c\)
CPU cores and \(r\)~GiB of RAM. The CPU effect at RAM level \(r\) is
\(100(L_{4,r}/L_{2,r}-1)\%\), and the RAM effect at CPU level \(c\) is
\(100(L_{c,6}/L_{c,2}-1)\%\). The descriptive CPU-by-RAM interaction is
\(100[(L_{4,6}/L_{4,2})/(L_{2,6}/L_{2,2})-1]\%\).
The design provides a controlled comparison among four emulator allocations
on one host. Its timed boundary covers Android launch, foreground return, and
graph display.

\subsection{Seed-Initialization Protocol}

The seed experiment uses arXiv:1706.03762, arXiv:2010.11929, and
arXiv:2106.09685. Each measurement begins with a new disposable PostgreSQL
database, an empty document store, a dedicated Redis instance and queue, a new
user, and cleared Android application data. Timing starts immediately before
the seed submission action and ends when the Android interface displays a
five-paper briefing identified as live backend content.
The fresh condition applies to Android, PostgreSQL, Redis, document storage,
queue, and user state. Host caches and live external-provider conditions
remain in their current state.

Each seed is measured once through the ordinary application and backend path.
Validation requires five unique paper identifiers, the same ordering in the
stored briefing, and a backend record for the input seed. The processing,
version, summary, chunk, job, and file state associated with every displayed
paper is retained with the measurement. The three observations are reported
individually and summarized by their median, minimum, maximum, and range.

\subsection{Event-Synchronization Protocol}

The event experiment uses ten batches containing thirty globally unique event
identifiers. A batch passes through five ordered stages: insertion into
the application's file-backed Room database, database close and reopen, an
HTTP~503 response from a controlled local server, upload to an isolated
FastAPI/PostgreSQL backend, and replay of the same identifiers from a new
file-backed local database. Only the named operation is timed in each stage.
Validation, database preparation, and artifact collection occur outside the
timing interval. The design yields ten values for each stage, summarized by
success count, median, minimum, maximum, and range.

\section{Success Conditions and Retained Artifacts}

A cached cold launch succeeds when the benchmark records a positive
fully-drawn time after the five-paper cached briefing has been displayed. A
foreground recovery succeeds when a positive initial-display time is recorded
and the expected paper count and content source are present while the process
and activity identifiers remain unchanged. Each session must contain exactly
five analyzed values for both launch scenarios, obtained from the prescribed
AndroidX metrics, and both benchmark tasks must complete successfully.

A graph timing succeeds when the renderer reaches the first validated visual
state with the expected node and edge counts. The recorded WebView state must
match the new or reused phase. Validation also requires the ascending node
order in the first block, the descending order in the second, positive
durations, complete pairs, matching render and paired-WebView identifiers, and
the full set of observations in each session.

A seed initialization succeeds when the interface displays exactly five unique
papers identified as live backend content. The corresponding backend state
must contain the same ordered briefing and input seed, together with the
processing status, paper version, summary, chunks, jobs, and stored files for
all five papers.

An event batch succeeds when all three identifiers are pending after the queue
write and database reopen, remain pending with one recorded attempt after the
HTTP~503 response, become synchronized after the isolated-backend upload, and are
recognized as three duplicates on replay. The controlled server must receive
the expected three-event request body. The live backend must report three
accepted and zero duplicate identifiers on the first upload, followed by zero
accepted and three duplicate identifiers when a new local database replays the
same UUIDs. The three replayed events must also reach the locally synchronized
state.

The retained evaluation material contains raw timing rows, native
Macrobenchmark output, graph test output, environment records, non-secret
configuration, machine-readable summaries, and figures generated from the
validated observations.

All three seed initializations satisfied the five-paper success condition.
The elapsed times were 28.46~s for arXiv:1706.03762, 41.73~s for
arXiv:2010.11929, and 36.50~s for arXiv:2106.09685. Their median was
36.50~s, with a minimum of 28.46~s, a maximum of 41.73~s, and a range of
13.27~s. All three runs used citation-graph candidates. The retained endpoint
state contained one or more versions, one summary, and a non-empty chunk set
for every displayed paper. Ten displayed papers were ready, and five were
available as partial records while one embedding job for each remained in
progress.

All ten retained event batches satisfied the five stage-specific success
conditions, yielding 50 valid timing rows. The 30 identifiers used for the
initial uploads were globally unique. The isolated backend contained 30 events
after the experiment, with ten records each for paper impression, paper open,
and question asked. First submission accepted all 30 identifiers, and replay
recognized all 30 as duplicates while the corresponding local rows reached the
synchronized state.
