\chapter{App Development and Testing}

The preceding chapter specified MNEME's architecture, interfaces, and interaction design.
This chapter describes the system as built: the Android client that carries the user-facing research loop, and the backend service that prepares literature, generates evidence-bounded assistance, and maintains the user's interest model.
The chapter then reports the testing evidence, moving from the tools and environments used, through interface and feature-acceptance results, to performance measurements.
Each mechanism is presented as an implemented response to one of the continuity challenges established in Chapter~1, and the testing sections show which responses the collected evidence supports.

\section{Front-end Development}

The MNEME client is a Kotlin application built on Jetpack Compose with Material~3 components.
Its role is deliberately narrow: it renders server-produced research artifacts --- briefings, paper records, summaries, grounded answers, and a bounded citation graph --- while keeping the reading session recoverable when the network, the backend, or the device lifecycle interrupts it.
This narrowness is the client-side answer to the interaction-continuity challenge.
Rather than duplicating server intelligence on the device, the client makes every visible state explicit about where its content came from and what the user can do next.

\subsection{Design Pattern}

The client follows the Model--View--ViewModel pattern with a repository layer between ViewModels and data sources.
Compose screens are pure functions of observable UI state; ViewModels own that state and reduce it from repository results; repositories mediate between Retrofit/OkHttp network services, Room persistence, and WorkManager background execution.
Two properties motivated this choice.
First, state transitions become unit-testable without an emulator: the controlled state experiments reported under Testing Results drive the ViewModel reducers directly with deterministic inputs.
Second, the offline and degraded paths acquire a single decision point --- the repository determines whether a screen receives live content, cached content, or an actionable error, and the outcome is carried in the state object rather than reconstructed in view code.

A distinctive element of the state model is its disclosure vocabulary.
Every content-bearing state distinguishes loading, live, cached, empty, fallback, and retryable-error conditions, and the distinction is rendered to the user rather than kept internal.
A briefing restored from the local cache is labeled as cached together with its freshness; a citation graph that degrades to its bounded local fallback says so on screen.
The application thereby applies to its own interface the same standard this thesis applies to evidence: cached or degraded content is never silently presented as live.

The repository layer also carries the client's consistency obligations.
Briefings and paper records are retained locally under explicit retention policies, and behavioral events are queued durably with client-generated UUID identity and retry bookkeeping.
A process death between capturing an event and uploading it therefore loses nothing, and a repeated upload is recognized by the server as a duplicate rather than a new signal.
Both properties are verified by the synchronization experiments reported later in this chapter.

\subsection{UI Controls}

The home surface is the briefing list, composed of cards that pair each recommended paper with its match information, a human-readable reason produced by the recommendation scorer, and one dominant open action.
The paper detail screen presents the structured summary with its source-linked elements, and the question-answering surface accepts a free-form question and renders the grounded answer together with its citation markers, so a reader can move from any claim to the evidence excerpt that supports it.
Verification labels sit adjacent to the claims they qualify rather than in a separate legend; this placement responds directly to the formative usability observations of Chapter~3.

The citation graph is the one control that leaves the Compose toolkit.
It is rendered by a locally bundled D3 visualization inside a WebView, so no network fetch is required for the visualization itself, while node selection is mirrored back into native state through a JavaScript bridge.
The native side therefore remains the single source of truth for the current selection, which enables the persistent ``open paper'' action, an unambiguous selected-node style, and the selection-restoration behavior verified under UI Testing.
Graph size is bounded at fifty nodes by the client request contract, keeping both rendering cost and user orientation manageable on a phone screen.

Interest management uses standard Material list and editing controls, reachable from the briefing surface, through which explicit topics can be added, edited, and removed.
Status and error surfaces reuse a small set of shared components, so the disclosure vocabulary described above looks identical wherever it appears.

\subsection{Navigation Controllers}

Navigation is implemented with Compose Navigation over type-safe routes.
The primary flow mirrors the research loop the system is designed around: briefing to paper detail, paper detail to question answering, paper detail or search to the citation graph, and briefing to interest and preference settings.
Each route carries typed arguments, such as the paper and briefing identities, rather than parsed strings, so a navigation regression surfaces as a compile-time failure rather than a runtime surprise.

Two navigation behaviors are load-bearing for the evaluation.
First, returning from a paper opened out of the graph restores the previous graph selection instead of resetting the view, so exploration context survives the round trip.
Second, background refresh and notification entry points land on the briefing surface with state restored from the local cache when the process has been killed in the interim.
The cold-start and resume latencies reported under Performance Testing therefore measure genuine user-visible recovery paths.

\subsection{Other Aspects}

Persistence is provided by Room with explicit schema migrations; briefing and paper caches carry offline metadata and retention policies.
Background work is scheduled through WorkManager, which owns periodic refresh and recovers interrupted work after process death; the durable event queue is drained by this machinery, and a reserved event returns to the pending state when its worker is interrupted.
Local notifications announce newly generated briefings, and first-run onboarding derives an initial arXiv category from a seed paper, preparing an initial set of papers through the backend pipeline before the first briefing is shown.

All device-level results in this chapter were collected on a single emulator configuration, described under Testing Tool.
Extending the notification permission flow across the full range of Android versions and validating behavior on a broader device matrix are engineering refinements that Chapter~5 lists among the outlook items.

\section{Back-end Development}

The backend is a Python/FastAPI service with PostgreSQL for durable storage, \texttt{pgvector} for vector search, Redis for caching, budget accounting, and job queues, and ARQ workers for background processing.
Its data model separates a paper's logical identity from its observed arXiv revisions: metadata ingestion registers papers, while long-running preparation --- parsing, section-aware chunking, summarization, and embedding --- runs in workers whose job state survives process restart.
Every derived artifact binds to a specific paper revision, and this binding is the structural foundation for the representation-continuity mechanisms that follow.

Representation continuity is enforced by determinism and identity rather than by convention.
Chunking is deterministic: the same parsed sections always produce the same chunk contents and content hashes, which makes the embedding stage idempotent and re-chunking comparable across runs.
Each embedding is stored in a 1536-dimension vector column paired with the identity of the model that produced it, under a database constraint that either both or neither are set, so a model migration cannot leave orphan vectors that silently poison similarity search.
Retrieval is revision-scoped by construction: an update to a paper produces new artifacts for the new revision instead of contaminating the old one, and question answering over one revision can never draw evidence from another.

Evidence continuity is implemented as a pipeline that is transparent about each of its stages.
Retrieval embeds the question and performs an exact cosine-ordered vector search over one revision's chunks, returning the top eight by similarity plus up to two early-document context anchors that preserve overview context; dense membership and anchor membership are tracked independently, because an early section can legitimately be both.
Reranking is a deliberately interpretable lexical blend rather than a learned cross-encoder: the final score weights vector similarity at 0.7 and the fraction of the question's content words present in the chunk at 0.3, ties break on the original retrieval order, and the top four chunks become evidence, with anchors outside that set appended rather than displacing question-specific evidence.
Generation is refused before any model call when no evidence reaches a minimum score of 0.25; the model may itself decline through a designated insufficient-evidence marker, and both paths return the same fixed refusal answer, so refusal is a single, recognizable outcome for the client.
After generation, citation verification checks every bracketed marker against the evidence list --- markers outside the list are dropped rather than repaired --- and compares each cited excerpt with the claim sentences that carry its marker.
A citation counts as source-matched when at least 30\% of the claim's content words appear in the cited chunk, and answers are labeled matched, partially matched, or insufficient.
Following the distinction drawn in citation-quality research~\cite{gao2023alce}, this is retrieved-source matching rather than semantic entailment: it verifies that generated claims are anchored in retrieved text, not that the text is scientifically correct.

Interest continuity is served by a recommendation scorer that composes three signals: explicit topic match with weight 0.45, cosine similarity between the user's learned behavior embedding and a paper's mean chunk embedding with weight 0.35, and publication recency with a one-week half-life at weight 0.2.
Missing signals redistribute their weight over the available ones, so a cold-start user still receives a meaningful ranking, and the ranking is deterministic with a stable tie-break.
Each recommendation carries human-readable reasons derived from its dominant signals rather than free-form generated text; these reasons are what the client renders beside each briefing entry, satisfying the scrutability requirement established in Chapter~3.

Provider routing, caching, and cost control cut across the whole AI layer.
Each task routes to a configured provider; Anthropic, OpenAI, and DeepSeek adapters are implemented, providers are inferred from model identifiers, and a misconfigured route fails at service startup rather than on the first user request.
Completions are cached in Redis --- for 24 hours for question answering and seven days for summaries --- with the prompt version participating in every cache key, so a template change invalidates cleanly.
A shared daily budget guard refuses provider calls once the configured daily cap (five US dollars by default) is spent, and exhaustion surfaces to the client as an explicit rate-limit response rather than a silent failure.
Every completion persists its provider, model snapshot, prompt version, input hash, token counts, estimated cost, and latency, so live operation is auditable from the database without additional instrumentation.

Finally, the backend includes the instrumentation to measure the assistance quality it provides.
A graded evaluation harness drives the full retrieval and grounded-answer pipeline over a frozen fixture corpus of fifteen manually curated cases across seven arXiv papers, twelve answerable and three whose correct behavior is refusal.
Each fixture pins the exact arXiv revision it was authored against; the evaluation resolves that exact revision and requires a complete, model-consistent embedding set before a case may run, reporting anything else as an explicit skip.
Retrieval quality is graded on dense results only, so a context anchor cannot convert a retrieval miss into a hit, and every report embeds the full run configuration --- provider, model, prompt version, embedding backend and model, retrieval and reranking settings, evidence threshold, and cache posture --- so that two runs are comparable exactly when their configurations match.
The harness further separates a served completion's original generation cost from the cost a run actually incurs, so cached completions cannot masquerade as live spend.

In summary, the four continuity challenges of Chapter~1 map onto concrete mechanisms: revision-bound artifacts and idempotent preparation provide representation continuity; bounded retrieval, refusal, and citation verification provide evidence continuity; the composed, explainable scorer provides interest continuity; and the job, event, and briefing boundaries provide the recoverable loop that interaction continuity requires.
The remainder of the chapter reports the evidence collected for these mechanisms.

\section{Testing Results}

Testing proceeds in four layers that answer progressively stronger questions.
Unit tests check deterministic transformations and boundary validation; repository and API tests check transactions, identity, and idempotency at service boundaries; integration and device tests check that client and server agree and that visible state follows backend outcomes; and research evaluations measure quality on frozen data or with participants.
The subsections below report the tools and environments first, then the interface results, the feature-acceptance results, and the performance measurements.

\subsection{Testing Tool}

The backend test suite runs under \texttt{pytest} in a \texttt{uv}-managed Python environment, with \texttt{ruff} for lint and formatting and \texttt{pyrefly} for type checking as static gates.
Provider-dependent code is tested against deterministic fake LLM and embedding providers and an in-memory Redis stand-in, so the software suite is fully reproducible without network access or provider credentials.
The suite comprises 470 tests, of which 463 pass in the standard environment and seven --- the PostgreSQL integration tests --- run only where a database is configured; the same suite gates every change in continuous integration.

The Android suite uses JUnit-based unit tests for ViewModel and repository logic, Compose UI tests for screen behavior, and Gradle-orchestrated static analysis with ktlint, detekt, and Android lint.
All device measurements were collected on an Android~14 (API~34) Google emulator with four virtual processors and a 192~MiB application heap.
For every measured group, warm-up iterations were run and discarded before retained samples were collected; reported medians are sample medians, and 95th percentiles use the nearest-rank definition.
Because a single emulator configuration was measured, the numbers support controlled comparison across conditions rather than estimates of physical-device variability.

\subsection{UI Testing}

The client's visible-state machinery was exercised in controlled trials that deliver deterministic results to the ViewModel layer and verify the resulting state and disclosure label.
Five content-state conditions --- a live seed transition, a cached warm start, a cached offline disclosure, a cached server-failure disclosure, and an invalid-cache error --- each completed 30 of 30 trials with the expected outcome, and the three citation-graph disclosure states (ready, fallback, and empty) likewise each completed 30 of 30 trials.
The disclosure vocabulary described under Design Pattern is therefore not merely available but reliably reached under each of its specified conditions.

Interactive graph behavior was verified by the graph and app-flow suite, which passed 11 of 11 tests, including node selection through the WebView bridge, navigation to a selected paper through the persistent open action, and restoration of the previous selection after returning from paper detail.
Together, these results establish the specified presentation and navigation behavior of every screen in the primary research loop.
The formative five-participant usability study that motivated the graph's redesign is design-stage evidence and is reported in Chapter~3.

\subsection{Acceptance Testing for Features}

Feature acceptance maps the acceptance criteria of Chapter~3 to executable checks.
For the literature-representation features, the decisive check is revision isolation: an API test asserts that question answering scoped to one paper revision cannot retrieve chunks belonging to another, which is the executable form of the guarantee that a revision update cannot silently change what the user is reading.
Idempotent re-preparation is covered by the deterministic chunking and content-hash tests in the backend suite.

For the assistance features, acceptance rests on refusal and verification behavior.
Tests cover refusal below the evidence threshold and through the model-side insufficient-evidence marker, citation-marker validation against the evidence list, and the source-match labeling of answers.
The cost boundary is verified on the public question route: integration tests assert that exhaustion of the daily budget surfaces as the specified rate-limit response for both the completion and the embedding paths, rather than as a generic failure.
The evaluation harness carries its own contract tests for fixture pinning, readiness checking with explicit skip reasons, configuration snapshotting, and its refusal to treat an empty evaluation as a successful one.

For the interaction loop, acceptance was measured end to end.
In controlled trials isolating the client queue from network variability, 30 of 30 trials each succeeded for the durable queue write, the injected retryable failure, the subsequent retry, and the duplicate replay.
A live trace then exercised the same client coordinator against a running backend in five repetitions: each queued three new events, recovered from an injected retryable failure, uploaded the batch, replayed the same identifiers, and read a briefing back through the standard client data path.
Every upload accepted three new identifiers, every replay was acknowledged as duplicate rather than re-ingested, and every readback returned live-backend content.
The digest returned during this trace was empty because the evaluation database held no paper inside the active fourteen-day briefing window; the trace therefore demonstrates the reachability and duplicate safety of the full cross-layer path, while recommendation content itself is exercised by the scorer tests described above.
Asynchronous job visibility was verified by the three-stage paper-preparation polling flow, which completed in 10 of 10 trials.

Client-side performance was measured on the emulator configuration described under Testing Tool.
Figure~\ref{fig:mobile-reliability} and Table~\ref{tab:mobile-reliability} report the resulting distributions.

On the backend side, model cost is treated as a first-class performance dimension, because a continuously running assistant is constrained as much by provider spend as by latency.
A static audit inventoried every provider call site --- the summarization worker, grounded question answering, query embedding, and batched chunk embedding; recommendation scoring reuses stored vectors and makes no provider call --- and estimated unit economics from provider list prices under the deployed input and output caps.
One paper summary on the default flagship route costs an estimated \$0.10, one grounded answer roughly \$0.028, and embedding a full paper roughly \$0.0003.
Against the default \$5 daily budget, a bulk-ingestion day of about fifty summaries can exhaust the cap on the flagship tier, whereas a lighter tier accommodates roughly 250 summaries per day, and a full fifteen-case evaluation run is estimated at \$0.34 versus \$0.07 across the two tiers.
The audit's principal consequence is a routing insight: bulk summarization is the dominant and least quality-sensitive spend, so moving it to a lighter tier while reserving the flagship tier for user-visible grounded answers would extend the same budget several-fold; the switch awaits a summary-quality comparison so that cost is not saved at the price of structured-output fidelity.
All dollar figures are estimates derived from a retained price snapshot with a companion script that recomputes them, and measured spend is available from the per-completion cost telemetry once the deployed pipeline runs at scale.

Three boundaries qualify these results.
Device measurements come from one emulator configuration; controlled timings measure client-internal transitions rather than network or frame latency; and the graded answer-quality evaluation --- retrieval hit rate, source-match rate, and refusal accuracy on the pinned fixture corpus --- awaits its live run against a deployed provider, with the harness, corpus, and configuration snapshotting already in place.
