\chapter{App Development and Testing}

The preceding chapter specified MNEME's architecture, interfaces, and interaction design.
This chapter describes the system as built: the Android client that carries the user-facing research loop, and the backend service that prepares literature, generates evidence-bounded assistance, and maintains the user's interest model.
The chapter then reports the testing evidence, moving from the tools and environments used, through interface and feature-acceptance results, to performance measurements.
The implementation is organized around the continuity challenges established in Chapter~1, and the testing sections examine the resulting behavior under recorded conditions.

\section{Front-end Development}

The MNEME client is a Kotlin application built on Jetpack Compose with Material~3 components.
It renders server-produced briefings, paper records, summaries, grounded answers, and bounded citation graphs.
It also preserves the reading state when the network, backend, or device lifecycle interrupts a session.
Document and model processing remain on the server, while the client discloses the origin of visible content and the next available action.

\subsection{Design Pattern}

The client follows the Model--View--ViewModel pattern with a repository layer between ViewModels and data sources.
Compose screens are pure functions of observable UI state; ViewModels own that state and reduce it from repository results; repositories mediate between Retrofit/OkHttp network services and Room persistence, while WorkManager invokes repository operations for background work.
Two properties motivated this choice.
State transitions become unit-testable without an emulator because the controlled state experiments reported under Testing Results drive the ViewModel reducers directly with deterministic inputs.
The repository also provides one decision point for offline and degraded paths: it determines whether a screen receives live content, cached content, or an actionable error, and carries the outcome in the state object.

A distinctive element of the state model is its disclosure vocabulary.
Every content-bearing state distinguishes loading, live, cached, empty, fallback, and retryable-error conditions, and the interface renders that distinction.
A briefing restored from the local cache is labeled as cached together with its freshness; a citation graph that degrades to its bounded local fallback says so on screen.
The application thereby applies to its own interface the same standard this thesis applies to evidence: cached or degraded content is never silently presented as live.

The repository layer also carries the client's consistency obligations.
Briefings and paper records are retained locally under explicit retention policies, and behavioral events are queued durably with client-generated UUID identity and retry bookkeeping.
A captured event remains queued across process death until it is acknowledged, and the server recognizes a repeated upload as a duplicate.
Both properties are verified by the synchronization experiments reported later in this chapter.

\subsection{UI Controls}

The home surface is the briefing list, composed of cards that pair each recommended paper with its match information, a human-readable reason produced by the recommendation scorer, and one dominant open action.
The paper detail screen presents the structured summary with its source-linked elements, and the question-answering surface accepts a free-form question and renders the grounded answer together with its citation markers, so a reader can move from a cited claim to its supporting evidence excerpt.
Verification labels sit adjacent to the claims they qualify, following the formative usability observations reported in Chapter~3.

The citation graph is the one control that leaves the Compose toolkit.
It is rendered by a locally bundled D3 visualization inside a WebView, so no network fetch is required for the visualization itself, while node selection is mirrored back into native state through a JavaScript bridge.
Before a graph is serialized for the WebView, the client validates unique node identities, the presence of the centre node, and the absence of dangling edges; the return bridge accepts only an identifier present in the displayed graph and posts the selection to the Android main thread.
The native side therefore remains the single source of truth for the current selection, which enables the persistent ``open paper'' action, a distinct selected-node style, and the selection-restoration behavior verified under UI Testing.
Graph size is bounded at fifty nodes by the client request contract, keeping both rendering cost and user orientation manageable on a phone screen.

Interest management uses standard Material list and editing controls, reachable from the briefing surface, through which explicit topics can be added, edited, and removed. The screen validates the draft locally and sends the complete topic list through the preference endpoint. The client preserves the independent followed-author list and immediately requests a recommended briefing from the canonical preference response. The updated preferences and briefing are stored together after that briefing returns. A successful state is shown only after this sequence completes; a failed request leaves the draft available for correction or retry. This sequence connects the visible edit to the recommendation path while leaving previously generated briefings unchanged.
Status and error surfaces reuse a small set of shared components, so the disclosure vocabulary described above looks identical wherever it appears.

\subsection{Navigation Controllers}

Navigation is implemented with Compose Navigation over type-safe routes.
The primary flow mirrors the research loop the system is designed around: the briefing opens a paper detail, the paper detail leads to question answering or the citation graph, a selected graph node opens its paper detail, and the briefing provides access to interest settings.
Routes that require context carry typed arguments such as the paper identity. This design lets the compiler detect type mismatches in route construction, while runtime tests verify the resulting navigation behavior.

Two navigation behaviors are central to the evaluation.
Returning from a paper opened out of the graph restores the previous graph selection, so exploration context survives the round trip.
Background refresh and notification entry points land on the briefing surface with state restored from the local cache when the process has been killed in the interim.
The cold-start and resume latencies reported under Performance Testing therefore measure genuine user-visible recovery paths.

\subsection{Other Aspects}

Persistence is provided by Room with explicit schema migrations; briefing and paper caches carry offline metadata and retention policies.
Background work is scheduled through WorkManager~\cite{androidWorkManager2026}, which owns periodic refresh and recovers interrupted work after process death; the durable event queue is drained by this machinery, and a reserved event returns to the pending state when its worker is interrupted.
Local notifications announce newly generated briefings, and first-run onboarding derives an initial arXiv category from a seed paper, preparing an initial set of papers through the backend pipeline before the first briefing is shown.

Paper resolution gives each route a single active load, so a late response for a previously selected paper cannot replace the newly selected one. Algorithm~\ref{alg:mobile-paper-resolution} states the implemented procedure realizing the origin-disclosure states designed in Chapter~3; the three-stage polling behavior it produces is measured under Performance Testing.

\begin{algorithm}[htbp]
  \caption{Origin-aware mobile paper resolution}
  \label{alg:mobile-paper-resolution}
  \KwIn{Selected paper identity \(p\), optional locally stored paper record}
  \KwOut{Typed presentation state with visible content origin}
  Cancel an earlier load, enter \emph{loading} for \(p\), and request its remote representation\;
  \If{the remote request fails}{\Return cached content when available; otherwise enter a retryable error state\;}
  Store a validated remote paper locally before presenting its derived content\;
  \While{the summary response identifies a queued or running job}{
    Display the preparation stage and poll the durable job after a bounded interval\;
    Propagate cancellation without converting it to a visible failure\;
  }
  \eIf{the representation is ready}{Render live content\;}{Enter a retryable error state with the safe public message\;}
\end{algorithm}

Device-level results were collected on Android~14 under the baseline and resource-controlled emulator configurations described under Testing Tool.
The study varies CPU and RAM within one emulation host.
Physical-device validation and notification-permission testing across additional Android versions remain future work.

\section{Back-end Development}

The backend is a Python/FastAPI service.
It uses PostgreSQL for durable storage, \texttt{pgvector} for vector search, Redis for caching, budget accounting, and job queues, and ARQ workers for background processing.
Its data model separates a paper's logical identity from its observed arXiv revisions: metadata ingestion registers papers, while long-running preparation, including parsing, section-aware chunking, summarization, and embedding, runs in workers whose job state survives process restart.
Chapter~3 fixed the design boundaries and public contracts of this service; the subsections below describe the implemented methods behind them, together with the parameters used in the evaluation.

\subsection{Revision-Safe Document Preparation}
\label{subsec:backend-preparation}

The data model distinguishes a logical paper \(p\) from an observed revision \(r\). The logical paper retains discovery metadata and stable external identifiers; the revision retains the source checksum, byte size, parser version, parse checksum, quality tier, and timestamps associated with one content state. A derived artifact \(a\) is interpreted as
\begin{equation}
  a = f\!\left(p,r,h,\theta\right),
  \label{eq:artifact-lineage}
\end{equation}
where \(h\) is the content checksum and \(\theta\) contains the transformation identity relevant to the artifact, such as parser, embedding model, prompt, or generator configuration. Equality of the logical paper identifier does not imply that two artifacts are interchangeable; reuse is valid only when the material lineage fields for the artifact class match. This binding is the structural foundation for the representation-continuity mechanisms that follow.

Algorithm~\ref{alg:document-preparation} states the preparation contract at the stage level.

\begin{algorithm}[htbp]
  \caption{Revision-safe document preparation}
  \label{alg:document-preparation}
  \KwIn{Logical paper \(p\), revision \(r\), validated source metadata, pipeline configuration \(\theta\)}
  \KwOut{A revision-scoped artifact state and durable identities for subsequent stages}
  Derive a durable job identity from \(p\), \(r\), the stage, and \(\theta\)\;
  \If{that job has succeeded}{\Return its published artifact state\;}
  Download and validate the revision under bounded size and time limits\;
  Publish the verified PDF atomically, then parse it into a versioned sidecar\;
  Record the parser identity, quality tier, checksum, and revision lineage\;
  Persist revision-scoped summary and chunk jobs before dispatching them\;
  \If{a controlled failure occurs}{
    Persist a stable failure state and retain any earlier valid artifact\;
  }
  \Return the current artifact state and child-job identities\;
\end{algorithm}

Durable identity is established before execution, and downstream work is recorded before delivery to a replaceable queue, so a process or queue failure can be retried without publishing partial bytes or losing the lineage between a parsed artifact and the exact revision that produced it.
Each processing stage receives an idempotency key computed from canonical inputs containing the stage, pipeline version, scope, and material identity: download identity includes the paper and revision, parse identity additionally includes the source checksum and parser version, and embedding identity includes the parsed artifact and the embedding model.
A uniqueness constraint causes concurrent submissions of the same logical work to converge on one durable job; the database records the public lifecycle, while replaceable queue attempts refer back to that job.
PDF and parsed-sidecar publication use temporary files and atomic replacement, so after a crash, storage contains either the complete previous artifact or an identifiable temporary file, and an incomplete file cannot appear as a valid published artifact.

Parsing must tolerate the variability of scientific PDFs in embedded text, column structure, marginal furniture, and heading typography.
CERMINE reconstructs document structure from page layout and text cues when PDF files encode no reliable semantic hierarchy~\cite{tkaczyk2015cermine}, and S2ORC demonstrates the downstream value of retaining paragraphs, section headers, and citation structure in machine-readable scholarly text~\cite{lo2020s2orc}.
The implemented parser combines PyMuPDF text blocks with pdfplumber layout information, reconstructs reading order for common two-column pages, filters likely marginal text blocks, and detects section boundaries from layout and heading cues.
It assigns a quality tier according to the evidence actually available: \texttt{structured} indicates useful text with credible sections, \texttt{text\_only} indicates useful text without sufficient structural confidence, and \texttt{abstract\_only} substitutes the provider abstract when the PDF cannot support full-text processing. A degraded document therefore remains usable at a disclosed, lower evidence fidelity.

Chunking is deterministic: the same parsed sections always produce the same chunk contents and content hashes, which makes the embedding stage idempotent and re-chunking comparable across runs.
Chunk construction splits oversized content near sentence boundaries with controlled overlap and retains section identity, page range, content hash, token estimate, and revision identity.
The deployed configuration bounds chunks at an estimated 450 tokens with a 60-token overlap; these values are the fixed study configuration rather than tuned optima, and chunk size and context-preserving chunking strategies are known to affect retrieval quality and answer faithfulness~\cite{wang2024bestpractices}.
Each embedding is stored in a 1536-dimension vector column paired with the identity of the model that produced it, under a database constraint that either both or neither are set, so a model migration cannot leave orphan vectors that silently poison similarity search.
Retrieval is revision-scoped by construction: an update to a paper produces new artifacts for the new revision and leaves the old revision unchanged. Question answering over one revision cannot draw evidence from another.

\subsection{Evidence-Grounded Question Answering}
\label{subsec:backend-qa}

Evidence continuity is implemented as a pipeline that is transparent about each of its stages.
Retrieval embeds the question and performs an exact cosine-ordered vector search over one revision's chunks, returning the top eight by similarity plus up to two early-document context anchors that preserve overview context; dense membership and anchor membership are tracked independently, because an early section can legitimately be both.

Reranking uses an interpretable lexical blend. For a question \(q\) and candidate chunk \(c\), the deterministic second-stage score combines normalized vector similarity \(D(q,c)\) with content-word overlap \(L(q,c)\):
\begin{equation}
  R(q,c)=0.7D(q,c)+0.3L(q,c).
  \label{eq:qa-rerank}
\end{equation}
Semantic proximity remains dominant, and lexical overlap supplies a task-specific correction without adding another learned model. Ties break on the original retrieval order, and the top four chunks become evidence; anchors outside that set are appended without displacing question-specific evidence.

Generation is refused before any model call when no evidence reaches a minimum score of 0.25; the model may itself decline through a designated insufficient-evidence marker, and both paths return the same fixed refusal answer, so refusal is a single, recognizable outcome for the client.
After generation, citation verification checks every bracketed marker against the evidence list. Markers outside the list are dropped, and each cited excerpt is compared with the claim sentences that carry its marker.
A citation counts as source-matched when at least 30\% of the claim's content words appear in the cited chunk, and answers are labeled matched, partially matched, or insufficient.
Retrieved context can coexist with unsupported or contradictory generation~\cite{niu2024ragtruth}, and following the distinction drawn in citation-quality research~\cite{gao2023alce}, this mechanism performs retrieved-source matching. It verifies lexical anchoring in retrieved text and does not establish semantic entailment or scientific correctness.

Algorithm~\ref{alg:qa-evidence} combines these stages into the implemented procedure.

\begin{algorithm}[htbp]
  \caption{Revision-scoped answer generation and source checking}
  \label{alg:qa-evidence}
  \KwIn{Paper \(p\), revision \(r\), question \(q\), embedding model \(m\), retrieval count \(k\), evidence threshold \(\tau\)}
  \KwOut{Answer text, valid source records, and a source-match state}
  Embed \(q\) and retrieve \(k\) candidates filtered by \(p\), \(r\), and \(m\)\;
  Add at most two non-duplicate overview anchors from revision \(r\)\;
  Compute \(R(q,c)\) from Equation~\ref{eq:qa-rerank} and order the evidence\;
  \If{the evidence is empty or its best score is below \(\tau\)}{\Return the fixed insufficient-evidence response\;}
  Generate an answer from the selected, numbered excerpts\;
  \If{the answer is empty or contains no usable marker}{\Return the fixed insufficient-evidence response\;}
  Discard invalid markers and measure local support for the remaining citations\;
  Assign \emph{matched}, \emph{partial}, or \emph{insufficient} from the valid-marker and overlap checks\;
  \Return the answer, valid source records, and assigned state\;
\end{algorithm}

The retrieval filter establishes revision membership, and the final checks establish marker validity and local lexical support; the returned state records the outcome of these checks for the client and for the graded evaluation reported under Testing Results.

\subsection{Behavioral Interest Model and Recommendation}
\label{subsec:backend-behavior}

Interest continuity is served by a recommendation scorer that composes three signals: explicit topic match, a contrastive behavioral affinity scaled by an evidence confidence, and publication recency.
The implementation responds to two long-standing observations about implicit feedback, that an observed action is not the same as confident preference~\cite{hu2008implicit} and that preferences drift over time~\cite{koren2009temporal}, with a deterministic, confidence-calibrated contrastive aggregation over content-space embeddings.
The signed single-timescale profile that preceded this design is kept available as a frozen baseline for the evaluation reported later in this chapter.

The model first distinguishes exposure from preference evidence.
An impression records that a paper was shown but contributes no positive weight; opens, saves, shares, and paper-scoped questions provide positive evidence; and a skip provides negative evidence only if an impression or open for the same paper occurred during the preceding seven days, which prevents an unobserved paper from being interpreted as a rejected topic.
Briefing dismissal remains outside the paper-interest profile because it has no paper identity.
Table~\ref{tab:behavior-weights} defines these fixed semantics. The magnitudes encode design priorities within this model, not measured certainty about the user's intent.

\begin{table}[htbp]
  \centering
  \small
  \caption{Event semantics in the contrastive behavioral aggregation.}
  \label{tab:behavior-weights}
  \begin{tabular}{@{}p{0.32\textwidth}p{0.18\textwidth}p{0.40\textwidth}@{}}
    \toprule
    \MnemeTableHeader{Observed event} & \MnemeTableHeader{Base weight} & \MnemeTableHeader{Interpretation} \\
    \midrule
    Paper impression & \(0\) & Exposure record used to qualify a subsequent skip. \\
    \MnemeRowRule
    Paper opened & \(+1\) & Positive evidence refined by bounded reading duration. \\
    \MnemeRowRule
    Paper saved & \(+3\) & Explicit positive retention signal. \\
    \MnemeRowRule
    Paper skipped & \(-1\) & Negative evidence only after recent exposure to the same paper. \\
    \MnemeRowRule
    Paper shared & \(+4\) & Strong explicit positive action. \\
    \MnemeRowRule
    Paper-scoped question asked & \(+2\) & Positive evidence of engagement with the selected paper. \\
    \MnemeRowRule

    \bottomrule
  \end{tabular}
  \normalsize
\end{table}

For eligible event \(i\), let \(b_i\) denote its signed base weight, \(m_i\) its duration multiplier, and \(\Delta_i\) its age in days. Only an open uses duration. If its observed duration is \(d_i\) seconds, clamped to the interval \([0,300]\), the continuous multiplier and dual-timescale temporal decay are
\begin{equation}
  m_i=0.5+\frac{\log(1+d_i/30)}{\log 11},
  \qquad
  g(\Delta_i)=0.70\,2^{-\Delta_i/14}+0.30\,2^{-\Delta_i/60}.
  \label{eq:behavior-temporal-weight}
\end{equation}
A missing duration gives \(m_i=1\), and a non-open event also uses unit duration multiplier. The effective signed evidence is \(\widetilde{w}_i=b_i m_i g(\Delta_i)\); observations older than 180 days contribute no profile evidence. The logarithmic transform lets reading time refine an open without allowing passive dwell time to outweigh an explicit save or share. Combining a 14-day and a 60-day half-life preserves sensitivity to recent changes while retaining a smaller persistent component. These fixed, replayable parameters define the configuration evaluated in this study.

A direct signed average has two undesirable properties: repeated actions on one paper can dominate through frequency, and positive and negative vectors can cancel into a near-zero representation that hides conflicting evidence. The first property is addressed by accumulating positive and negative mass separately for each paper \(j\), then applying diminishing returns:
\begin{equation}
  M_j^+=\sum_{i\in j}\max(\widetilde{w}_i,0),
  \quad M_j^-=\sum_{i\in j}\max(-\widetilde{w}_i,0),
  \quad a_j^+=1-e^{-M_j^+/3},
  \quad a_j^-=1-e^{-M_j^-}.
  \label{eq:behavior-saturation}
\end{equation}
The resulting supports \(a_j^+\) and \(a_j^-\) are bounded below one, so another interaction with an already well-supported paper has less influence than evidence from a distinct paper. Let \(v_j\) be the compatible mean chunk embedding of paper \(j\). Positive and negative interest states are then maintained as independently normalized support-weighted centroids:
\begin{equation}
  u^+=\operatorname{norm}\!\left(\sum_j a_j^+v_j\right),
  \qquad
  u^-=\operatorname{norm}\!\left(\sum_j a_j^-v_j\right).
  \label{eq:behavior-contrastive-profile}
\end{equation}
Here, \(\operatorname{norm}(x)=x/\lVert x\rVert_2\) for a non-degenerate vector; a channel with no compatible evidence is absent. Separate centroids preserve attraction and avoidance when the observations conflict.

The profile also estimates how much influence its behavioral evidence should receive. Let \(M=\sum_j(a_j^++a_j^-)\) be total embedded support, \(D\) the number of distinct embedded papers with non-zero support, and \(Q\) the fraction of eligible evidence papers for which a compatible embedding is available. The bounded confidence is
\begin{equation}
  C=Q\sqrt{\left(1-e^{-M/3}\right)\left(1-e^{-D/3}\right)},
  \qquad 0\leq C\leq 1.
  \label{eq:behavior-confidence}
\end{equation}
This construction requires both evidence mass and diversity, while incomplete embedding coverage reduces confidence directly. Repeated engagement with one paper can strengthen its support but cannot immediately grant the behavioral component its full nominal weight. Missing embeddings do not delete raw observations; they remain available for a later deterministic replay.

Recommendation keeps explicit preference and inferred behavior as separate components. For candidate paper \(p\) with embedding \(v_p\), the contrastive affinity compares alignment with the positive and negative centroids:
\begin{equation}
  A(p)=\operatorname{clip}_{[0,1]}\!\left(0.5+0.5\left[\cos(u^+,v_p)-\cos(u^-,v_p)\right]\right).
  \label{eq:behavior-affinity}
\end{equation}
An absent channel contributes zero cosine similarity. If \(T(p)\) is explicit-topic match and \(F(p)=2^{-d/7}\) is recency for publication age \(d\), define component values \((x_T,x_B,x_F)=(T(p),A(p),F(p))\) and nominal weights \((\alpha_T,\alpha_B,\alpha_F)=(0.45,0.35C,0.20)\). For the set \(\mathcal{K}(p)\) of available components, the implemented score is
\begin{equation}
  S(p)=\frac{\sum_{k\in\mathcal{K}(p)}\alpha_k x_k}{\sum_{k\in\mathcal{K}(p)}\alpha_k}.
  \label{eq:recommendation-score}
\end{equation}
A missing topic or behavioral component is omitted from \(\mathcal{K}(p)\), so a cold-start user still receives a meaningful ranking, and a zero-confidence profile follows the cold-start signals without giving behavioral weight to one weak observation. Stable paper UUID ordering resolves exact score ties.
Work on scrutable recommendation profiles motivates exposing and correcting the representation behind a recommendation~\cite{ramos2024scrutable}. The implementation provides the narrower property that explicit topics remain editable and that each recommendation carries human-readable reasons selected only from components that participated in its score; the client renders these deterministic reasons beside each briefing entry.

Algorithm~\ref{alg:behavior-ranking} separates the replayable computation from its interpretation.

\begin{algorithm}[htbp]
  \caption{Replayable contrastive preference update and candidate ranking}
  \label{alg:behavior-ranking}
  \KwIn{Deduplicated event history \(E\), compatible paper embeddings \(V\), reference time \(t\), candidate set \(P\)}
  \KwOut{Ranked candidates and a versioned evidence summary}
  \ForEach{event \(e_i\in E\)}{
    Exclude stale events and events without a usable paper identity\;
    Admit a negative skip only when recent exposure exists for the same paper\;
    Accumulate signed, time-decayed evidence \(\widetilde{w}_i=b_i m_i g(\Delta_i)\) by paper\;
  }
  Apply the saturation functions in Equation~\ref{eq:behavior-saturation} per paper\;
  Construct \(u^+\) and \(u^-\) from compatible embeddings and compute confidence \(C\)\;
  \ForEach{candidate \(p\in P\)}{
    Compute \(S(p)\) from the available topic, behavioral, and recency components\;
    Derive a reason only from components that participated in \(S(p)\)\;
  }
  \Return candidates ordered by score and stable paper identity, with confidence and evidence counts\;
\end{algorithm}

The event history and compatible embeddings determine the result for a fixed reference time, and the output carries evidence counts and confidence, so the mechanism evaluation reported under Testing Results can inspect why behavioral influence increased, decreased, or remained absent without treating interaction weights as direct measurements of human preference.

\subsection{Bounded Citation-Graph Construction}
\label{subsec:backend-graph}

The citation graph that the client renders is produced by a deterministic algorithm layer over persisted citation observations. An edge records that a source paper cites a target paper. A provider observation may initially identify one citation endpoint only by an external identifier, but at least one endpoint is local; the unresolved observation is retained until it can be associated with a local paper. Self-edges and duplicates are removed during resolution, and only edges whose endpoints resolve to local paper identities enter the public graph, so a missing external node does not imply an absent citation.
The public graph service currently supplies persisted citation edges and no keyword co-occurrence input, so its returned edges represent resolved citation relations.

Citation edges are damped by the inverse logarithm of the target's citation in-degree, reducing the influence of ubiquitously cited papers on layout and ranking.
A bounded best-first expansion from the requested center paper selects the neighborhood by cumulative edge weight, so a truncated result retains the highest-weight paths reached from the center.
Surviving nodes receive cluster identities from a weighted adaptation of label propagation, a local community-detection method in which nodes repeatedly adopt labels supported by their neighbours~\cite{raghavan2007label}, using deterministic tie-breaking and at most ten update rounds; the grouping is a presentation aid, not a semantic topic ground truth. Rank scores come from weighted degree centrality normalized to the unit interval.
The public route bounds traversal depth at two and the node limit at 200, and the client's request contract asks for at most fifty nodes. These limits bound the graph passed to the device, and a chronological citation-only view with a disclosed algorithm status is the deterministic fallback when enrichment fails.

Algorithm~\ref{alg:citation-graph} states the construction.

\begin{algorithm}[htbp]
  \caption{Bounded citation-graph view construction}
  \label{alg:citation-graph}
  \KwIn{Centre paper \(p_0\), resolved local citation snapshot \(G=(V,E)\), depth \(d\), node limit \(L\)}
  \KwOut{A bounded node-and-edge view with algorithm status}
  Clamp \(d\) and \(L\), then assign each edge a hub-damped citation weight\;
  Expand bidirectionally from \(p_0\) by cumulative path strength until depth or node limit is reached\;
  Retain edges whose endpoints both occur in the selected node set\;
  Initialize every selected node with a unique community label\;
  \For{at most ten rounds}{
    Update each label from the strongest weighted neighbouring label\;
    Resolve ties deterministically and stop when no label changes\;
  }
  Rank nodes by normalized weighted degree while preserving \(p_0\) as the centre\;
  \If{enrichment fails}{Construct a bounded chronological view and set status to \emph{fallback}\;}
  \Return selected papers, directed edges, community labels, ranks, and status\;
\end{algorithm}

The server-side view leaves spatial layout to the client, and deterministic tie-breaking gives the same logical snapshot the same ordering and grouping. Raw citation observations remain persistent, while the enriched view is computed per request; this avoids invalidation rules for stored layouts at the cost of repeated computation over the selected neighborhood.

\subsection{Provider Routing, Caching, and Evaluation Instrumentation}
\label{subsec:backend-provider}

Provider routing, caching, and cost control cut across the whole AI layer.
Model-facing stages communicate through provider-independent request and result objects. Each task routes to a configured model; Anthropic, OpenAI, and DeepSeek adapters are implemented, providers are inferred from model identifiers, and route validation occurs at service startup.
Completions are cached in Redis for 24 hours for question answering and seven days for summaries, under a canonical key containing the task, provider, model, prompt version, messages, and output limit, so a template change invalidates cleanly.
A shared daily budget guard refuses provider calls once the configured daily cap (five US dollars by default) is spent, and exhaustion surfaces to the client as an explicit rate-limit response. The counter is an operational stop-loss rather than a strict bound, because concurrent in-flight requests can still cross the threshold.

Every completion persists its provider, model snapshot, prompt version, input hash, token counts, estimated cost, and latency, so live operation is auditable from the database without additional instrumentation.
Question messages additionally retain the answer, citations, and source-match state, but omit the complete generation request; the records support audit and partial reconstruction rather than bit-for-bit regeneration.
Raw behavioral history and secrets are excluded from model prompts.

Finally, the backend includes the instrumentation to measure the assistance quality it provides.
A graded evaluation harness drives the full retrieval and grounded-answer pipeline over a frozen fixture corpus of fifteen manually curated cases across seven arXiv papers, twelve answerable and three whose correct behavior is refusal.
Each fixture pins the exact arXiv revision it was authored against; the evaluation resolves that exact revision and requires a complete, model-consistent embedding set before a case may run, reporting anything else as an explicit skip.
Retrieval quality is graded on dense results only, so a context anchor cannot convert a retrieval miss into a hit. Each evaluation record includes the provider, model, prompt version, embedding backend and model, retrieval and reranking settings, evidence threshold, and cache condition.
The harness further separates a served completion's original generation cost from the cost a run actually incurs, so cached completions cannot masquerade as live spend.

In summary, the four continuity challenges of Chapter~1 map onto concrete mechanisms: revision-bound artifacts and idempotent preparation provide representation continuity; bounded retrieval, refusal, and citation verification provide evidence continuity; the composed, explainable scorer provides interest continuity; and the job, event, and briefing boundaries, together with the bounded deterministic graph views, provide the recoverable loop that interaction continuity requires.
The remainder of the chapter reports the evidence collected for these mechanisms.

\section{Testing Results}

Testing proceeds in four layers that answer progressively stronger questions.
Unit tests check deterministic transformations and boundary validation; repository and API tests check transactions, identity, and idempotency at service boundaries; integration and device tests check that client and server agree and that visible state follows backend outcomes; and research evaluations measure mechanism behavior and output quality on frozen fixtures under recorded configurations.

\subsection{Testing Tool}

The backend test suite runs under \texttt{pytest} in a \texttt{uv}-managed Python environment, with \texttt{ruff} for lint and formatting and \texttt{pyrefly} for type checking as static gates.
Provider-dependent code is tested against deterministic fake LLM and embedding providers and an in-memory Redis stand-in, so the software suite is fully reproducible without network access or provider credentials.
The executed suite comprised 533 tests, all of which passed against PostgreSQL~16 with \texttt{pgvector}, with no failure or skip.
Full-suite line coverage was 89.05\% and branch coverage 76.15\%. Recommendation scoring reached 97.87\% line coverage and the evaluation harness reached 97.85\%; coverage provides supporting software evidence and does not establish semantic correctness.
The behavior-model database migration was additionally exercised in both directions, upgrading to its target revision, downgrading one revision, and upgrading again without error.

The Android suite uses JUnit-based unit tests for ViewModel and repository logic, Compose UI tests for screen behavior, and Gradle-orchestrated static analysis with ktlint, detekt, and Android lint.
The baseline device experiment used an Android~14 (API~34) Google emulator with four virtual processors and a 192~MiB application heap.
For every measured group, warm-up iterations were run and discarded before samples were collected; reported medians are sample medians, and 95th percentiles use the nearest-rank definition.
Instrumentation tests wrote one record per measured operation, and a separate analysis program validated the expected sample counts and success fields before computing any summary statistic.
All 810 controlled samples and all 25 live-backend stages in this baseline experiment met their stated success conditions.

A second Android experiment varied emulated CPU and RAM in a \(2\times2\) factorial design.
It compared two and four virtual processor cores at 2 and 6~GiB of emulator RAM while holding Android~14, the Pixel~6 profile, the Google APIs x86\_64 image, screen size, density, application heap, build, host, and measurement code fixed.
Four counterbalanced blocks produced four independent wiped-data cold-boot sessions for each configuration.
Each session contained 810 repeated controlled samples. The analysis summarized them by a per-session median, preserving the emulator session as the independent unit.
The analysis therefore uses four independent session summaries per cell.
Finite bootstrap intervals enumerate all resamples of those four values, and factor changes are interpreted descriptively because the sessions come from one emulation host.
All 12{,}960 samples satisfied their predefined success conditions, and each configuration also passed the eleven graph and app-flow tests in its first block.

Three research-evaluation harnesses measure behavioral ranking, explicit-interest correction, and grounded assistance.
The behavior model is evaluated with twelve deterministic synthetic traces spanning cold start, stable interest, recent interest shift, exposed and unexposed negative feedback, repeated interactions with one paper, contradictory feedback, incomplete embedding coverage, and duplicate replay.
Four headline systems, recency only, explicit-topic matching with recency, the earlier signed single-timescale profile, and the confidence-calibrated contrastive model of Section~\ref{subsec:backend-behavior}, invoke the production aggregation and recommendation functions. Five single-mechanism ablations use the same functions.
Ranking quality is measured with graded nDCG@5, Recall@5, and reciprocal rank. The cold-start trace defines no relevance judgments and is excluded, leaving eleven applicable traces. Paired differences carry fixed-seed percentile bootstrap intervals over 10{,}000 resamples and are interpreted descriptively because the scenarios were designed for mechanism coverage and were not sampled from a user population.

The explicit-interest experiment isolates direct correction from behavioral inference. Its frozen fixture contains eight synthetic candidates, two each for attention, quantum computing, robotics, and databases, with publication time held constant. The production ranking function evaluates four successive profiles: attention alone; attention with quantum added; quantum replaced by robotics; and robotics deleted. One record is retained for every candidate and state, including rank, score, reasons, and the presence of the expected topic-match reason. Four transition checks state the expected score direction before analysis. API tests separately replace the stored topic list and request the next recommended digest, while repository tests verify normalization, persistence, and rejection of a digest older than the preference update.

The grounded-assistance harness drives the deployed retrieval and answer pipeline over the fifteen pinned fixtures described under Back-end Development.
Its live flagship run used Claude Opus~4.8 (\nolinkurl{claude-opus-4-8}) with prompt version \texttt{qa-v2}, top-eight retrieval with two context anchors, rerank to four evidence chunks, a 0.25 evidence threshold, a 512-token output cap, and local \texttt{fastembed} embeddings. The 384-dimension vectors are L2-normalized and zero-padded into the 1{,}536-dimension store, which leaves cosine ordering unchanged.
The complete configuration is stored with the evaluation record, and every completion in the reported run was generated live with no cached contribution.

Measured spend at scale remains available from the per-completion cost telemetry.

The results establish the measured behavior of the implemented system across client recovery, graph interaction, preference correction, event synchronization, grounded assistance, and provider routing.
Device measurements use one Android version, device profile, and host; controlled state timings exclude network and frame latency. The behavior-model and explicit-correction evaluations use designed traces and balanced synthetic candidates, while the graded answer-quality evaluation reports one run on each of two provider routes over a fifteen-case corpus. These experiments provide reproducible evidence for the principal mechanisms and identify the areas that require broader device, user, and corpus validation.
