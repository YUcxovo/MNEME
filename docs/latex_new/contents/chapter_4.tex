\chapter{App Development and Testing}

The preceding chapter specified MNEME's architecture, interfaces, and interaction design.
This chapter describes the system as built: the Android client that carries the user-facing research loop, and the backend service that prepares literature, generates evidence-bounded assistance, and maintains the user's interest model.
The chapter then reports the testing evidence, moving from the tools and environments used, through interface and feature-acceptance results, to performance measurements.
The implementation is organized around the continuity challenges established in Chapter~1, and the testing sections examine the resulting behavior under recorded conditions.

\section{Front-end Development}

The MNEME client is a Kotlin application built on Jetpack Compose with Material~3 components.
It renders server-produced briefings, paper records, summaries, grounded answers, and bounded citation graphs.
It also preserves the reading state when the network, backend, or device lifecycle interrupts a session.
Document and model processing remain on the server, while the client discloses the origin of visible content and the next available action.

\subsection{Design Pattern}

The client follows the Model--View--ViewModel pattern with a repository layer between ViewModels and data sources.
Compose screens are pure functions of observable UI state; ViewModels own that state and reduce it from repository results; repositories mediate between Retrofit/OkHttp network services and Room persistence, while WorkManager invokes repository operations for background work.
Two properties motivated this choice.
State transitions become unit-testable without an emulator because the controlled state experiments reported under Testing Results drive the ViewModel reducers directly with deterministic inputs.
The repository also provides one decision point for offline and degraded paths: it determines whether a screen receives live content, cached content, or an actionable error, and carries the outcome in the state object.

A distinctive element of the state model is its disclosure vocabulary.
Every content-bearing state distinguishes loading, live, cached, empty, fallback, and retryable-error conditions, and the interface renders that distinction.
A briefing restored from the local cache is labeled as cached together with its freshness; a citation graph that degrades to its bounded local fallback says so on screen.
The application thereby applies to its own interface the same standard this thesis applies to evidence: cached or degraded content is never silently presented as live.

The repository layer also carries the client's consistency obligations.
Briefings and paper records are retained locally under explicit retention policies, and behavioral events are queued durably with client-generated UUID identity and retry bookkeeping.
A captured event remains queued across process death until it is acknowledged, and the server recognizes a repeated upload as a duplicate.
Both properties are verified by the synchronization experiments reported later in this chapter.

\subsection{UI Controls}

The home surface is the briefing list, composed of cards that pair each recommended paper with its match information, a human-readable reason produced by the recommendation scorer, and one dominant open action.
The paper detail screen presents the structured summary with its source-linked elements, and the question-answering surface accepts a free-form question and renders the grounded answer together with its citation markers, so a reader can move from a cited claim to its supporting evidence excerpt.
Verification labels sit adjacent to the claims they qualify. This placement responds directly to the formative usability observations of Chapter~3.

The citation graph is the one control that leaves the Compose toolkit.
It is rendered by a locally bundled D3 visualization inside a WebView, so no network fetch is required for the visualization itself, while node selection is mirrored back into native state through a JavaScript bridge.
The native side therefore remains the single source of truth for the current selection, which enables the persistent ``open paper'' action, a distinct selected-node style, and the selection-restoration behavior verified under UI Testing.
Graph size is bounded at fifty nodes by the client request contract, keeping both rendering cost and user orientation manageable on a phone screen.

Interest management uses standard Material list and editing controls, reachable from the briefing surface, through which explicit topics can be added, edited, and removed. The screen validates the draft locally and sends the complete topic list through the preference endpoint. The client preserves the independent followed-author list and immediately requests a recommended briefing from the canonical preference response. The updated preferences and briefing are stored together after that briefing returns. A successful state is shown only after this sequence completes; a failed request leaves the draft available for correction or retry. This sequence connects the visible edit to the recommendation path while leaving previously generated briefings unchanged.
Status and error surfaces reuse a small set of shared components, so the disclosure vocabulary described above looks identical wherever it appears.

\subsection{Navigation Controllers}

Navigation is implemented with Compose Navigation over type-safe routes.
The primary flow mirrors the research loop the system is designed around: the briefing opens a paper detail, the paper detail leads to question answering or the citation graph, a selected graph node opens its paper detail, and the briefing provides access to interest settings.
Routes that require context carry typed arguments such as the paper identity. This design lets the compiler detect type mismatches in route construction, while runtime tests verify the resulting navigation behavior.

Two navigation behaviors are central to the evaluation.
Returning from a paper opened out of the graph restores the previous graph selection, so exploration context survives the round trip.
Background refresh and notification entry points land on the briefing surface with state restored from the local cache when the process has been killed in the interim.
The cold-start and resume latencies reported under Performance Testing therefore measure genuine user-visible recovery paths.

\subsection{Other Aspects}

Persistence is provided by Room with explicit schema migrations; briefing and paper caches carry offline metadata and retention policies.
Background work is scheduled through WorkManager, which owns periodic refresh and recovers interrupted work after process death; the durable event queue is drained by this machinery, and a reserved event returns to the pending state when its worker is interrupted.
Local notifications announce newly generated briefings, and first-run onboarding derives an initial arXiv category from a seed paper, preparing an initial set of papers through the backend pipeline before the first briefing is shown.

Device-level results were collected on Android~14 under the baseline and resource-controlled emulator configurations described under Testing Tool.
The study varies CPU and RAM within one emulation host.
Physical-device validation and notification-permission testing across additional Android versions remain future work.

\section{Back-end Development}

The backend is a Python/FastAPI service.
It uses PostgreSQL for durable storage, \texttt{pgvector} for vector search, Redis for caching, budget accounting, and job queues, and ARQ workers for background processing.
Its data model separates a paper's logical identity from its observed arXiv revisions: metadata ingestion registers papers, while long-running preparation, including parsing, section-aware chunking, summarization, and embedding, runs in workers whose job state survives process restart.
Every derived artifact binds to a specific paper revision, and this binding is the structural foundation for the representation-continuity mechanisms that follow.

Determinism and explicit identity enforce representation continuity.
Chunking is deterministic: the same parsed sections always produce the same chunk contents and content hashes, which makes the embedding stage idempotent and re-chunking comparable across runs.
Each embedding is stored in a 1536-dimension vector column paired with the identity of the model that produced it, under a database constraint that either both or neither are set, so a model migration cannot leave orphan vectors that silently poison similarity search.
Retrieval is revision-scoped by construction: an update to a paper produces new artifacts for the new revision and leaves the old revision unchanged. Question answering over one revision cannot draw evidence from another.

Evidence continuity is implemented as a pipeline that is transparent about each of its stages.
Retrieval embeds the question and performs an exact cosine-ordered vector search over one revision's chunks, returning the top eight by similarity plus up to two early-document context anchors that preserve overview context; dense membership and anchor membership are tracked independently, because an early section can legitimately be both.
Reranking uses an interpretable lexical blend. The final score weights vector similarity at 0.7 and the fraction of the question's content words present in the chunk at 0.3, ties break on the original retrieval order, and the top four chunks become evidence. Anchors outside that set are appended without displacing question-specific evidence.
Generation is refused before any model call when no evidence reaches a minimum score of 0.25; the model may itself decline through a designated insufficient-evidence marker, and both paths return the same fixed refusal answer, so refusal is a single, recognizable outcome for the client.
After generation, citation verification checks every bracketed marker against the evidence list. Markers outside the list are dropped, and each cited excerpt is compared with the claim sentences that carry its marker.
A citation counts as source-matched when at least 30\% of the claim's content words appear in the cited chunk, and answers are labeled matched, partially matched, or insufficient.
Following the distinction drawn in citation-quality research~\cite{gao2023alce}, this mechanism performs retrieved-source matching. It verifies lexical anchoring in retrieved text and does not establish semantic entailment or scientific correctness.

Interest continuity is served by a recommendation scorer that composes three signals: explicit topic match with nominal weight 0.45, a contrastive behavioral affinity with nominal weight \(0.35C\), and publication recency with a one-week half-life at weight 0.2.
The behavioral affinity compares a candidate's mean chunk embedding with the profile's positive and negative interest centroids, and confidence \(C\) scales its influence.
The behavior embedding is produced by deterministic, confidence-calibrated contrastive aggregation.
The design accounts for sparse observations and changes in interests over time.
It treats a skip as negative evidence only after recorded exposure and limits the effect of repeated activity on one paper.
The aggregation maintains separate positive and negative channels, applies dual-timescale decay, saturates per-paper support, and carries evidence confidence into the final recommendation score.
The signed single-timescale profile that preceded this design is kept available as a frozen baseline for the evaluation reported later in this chapter.
Missing signals redistribute their weight over the available ones, so a cold-start user still receives a meaningful ranking, and the ranking is deterministic with a stable tie-break.
Each recommendation carries human-readable reasons derived from its dominant scoring signals. The client renders these deterministic reasons beside each briefing entry, satisfying the scrutability requirement established in Chapter~3.

The citation graph that the client renders is produced by a deterministic algorithm layer. Its pure functions support citation-edge weighting, optional keyword co-occurrence, bounded selection, clustering, and ranking. The public graph service currently supplies persisted citation edges and no keyword co-occurrence input, so its returned edges represent resolved citation relations.
Citation edges are damped by the inverse logarithm of the target's citation in-degree, reducing the influence of ubiquitously cited papers on layout and ranking.
A bounded best-first expansion from the requested center paper selects the neighborhood by cumulative edge weight, so a truncated result retains the highest-weight paths reached from the center.
Surviving nodes receive cluster identities from a deterministic weighted label propagation with a bounded number of rounds and rank scores from weighted degree centrality normalized to the unit interval.
The public route bounds traversal depth at two and the node limit at 200, and the client's request contract asks for at most fifty nodes. These limits bound the graph passed to the device.

Provider routing, caching, and cost control cut across the whole AI layer.
Each task routes to a configured provider; Anthropic, OpenAI, and DeepSeek adapters are implemented, providers are inferred from model identifiers, and route validation occurs at service startup.
Completions are cached in Redis for 24 hours for question answering and seven days for summaries. The prompt version participates in every cache key, so a template change invalidates cleanly.
A shared daily budget guard refuses provider calls once the configured daily cap (five US dollars by default) is spent, and exhaustion surfaces to the client as an explicit rate-limit response.
Every completion persists its provider, model snapshot, prompt version, input hash, token counts, estimated cost, and latency, so live operation is auditable from the database without additional instrumentation.

Finally, the backend includes the instrumentation to measure the assistance quality it provides.
A graded evaluation harness drives the full retrieval and grounded-answer pipeline over a frozen fixture corpus of fifteen manually curated cases across seven arXiv papers, twelve answerable and three whose correct behavior is refusal.
Each fixture pins the exact arXiv revision it was authored against; the evaluation resolves that exact revision and requires a complete, model-consistent embedding set before a case may run, reporting anything else as an explicit skip.
Retrieval quality is graded on dense results only, so a context anchor cannot convert a retrieval miss into a hit. Each evaluation record includes the provider, model, prompt version, embedding backend and model, retrieval and reranking settings, evidence threshold, and cache condition.
The harness further separates a served completion's original generation cost from the cost a run actually incurs, so cached completions cannot masquerade as live spend.

In summary, the four continuity challenges of Chapter~1 map onto concrete mechanisms: revision-bound artifacts and idempotent preparation provide representation continuity; bounded retrieval, refusal, and citation verification provide evidence continuity; the composed, explainable scorer provides interest continuity; and the job, event, and briefing boundaries, together with the bounded deterministic graph views, provide the recoverable loop that interaction continuity requires.
The remainder of the chapter reports the evidence collected for these mechanisms.

\section{Testing Results}

Testing proceeds in four layers that answer progressively stronger questions.
Unit tests check deterministic transformations and boundary validation; repository and API tests check transactions, identity, and idempotency at service boundaries; integration and device tests check that client and server agree and that visible state follows backend outcomes; and research evaluations measure mechanism behavior and output quality on frozen fixtures under recorded configurations.

\subsection{Testing Tool}

The backend test suite runs under \texttt{pytest} in a \texttt{uv}-managed Python environment, with \texttt{ruff} for lint and formatting and \texttt{pyrefly} for type checking as static gates.
Provider-dependent code is tested against deterministic fake LLM and embedding providers and an in-memory Redis stand-in, so the software suite is fully reproducible without network access or provider credentials.
The executed suite comprised 533 tests, all of which passed against PostgreSQL~16 with \texttt{pgvector}, with no failure or skip.
Full-suite line coverage was 89.05\% and branch coverage 76.15\%. Recommendation scoring reached 97.87\% line coverage and the evaluation harness reached 97.85\%; coverage provides supporting software evidence and does not establish semantic correctness.
The behavior-model database migration was additionally exercised in both directions, upgrading to its target revision, downgrading one revision, and upgrading again without error.

The Android suite uses JUnit-based unit tests for ViewModel and repository logic, Compose UI tests for screen behavior, and Gradle-orchestrated static analysis with ktlint, detekt, and Android lint.
The baseline device experiment used an Android~14 (API~34) Google emulator with four virtual processors and a 192~MiB application heap.
For every measured group, warm-up iterations were run and discarded before samples were collected; reported medians are sample medians, and 95th percentiles use the nearest-rank definition.
Instrumentation tests wrote one record per measured operation, and a separate analysis program validated the expected sample counts and success fields before computing any summary statistic.
All 810 controlled samples and all 25 live-backend stages in this baseline experiment met their stated success conditions.

A second Android experiment varied emulated CPU and RAM in a \(2\times2\) factorial design.
It compared two and four virtual processor cores at 2 and 6~GiB of emulator RAM while holding Android~14, the Pixel~6 profile, the Google APIs x86\_64 image, screen size, density, application heap, build, host, and measurement code fixed.
Four counterbalanced blocks produced four independent wiped-data cold-boot sessions for each configuration.
Each session contained 810 repeated controlled samples. The analysis summarized them by a per-session median, preserving the emulator session as the independent unit.
The analysis therefore uses four independent session summaries per cell.
Finite bootstrap intervals enumerate all resamples of those four values, and factor changes are interpreted descriptively because the sessions come from one emulation host.
All 12{,}960 samples satisfied their predefined success conditions, and each configuration also passed the eleven graph and app-flow tests in its first block.

Three research-evaluation harnesses measure behavioral ranking, explicit-interest correction, and grounded assistance.
The behavior model is evaluated with twelve deterministic synthetic traces spanning cold start, stable interest, recent interest shift, exposed and unexposed negative feedback, repeated interactions with one paper, contradictory feedback, incomplete embedding coverage, and duplicate replay.
Four headline systems, recency only, explicit-topic matching with recency, the earlier signed single-timescale profile, and the confidence-calibrated contrastive model of Chapter~3, invoke the production aggregation and recommendation functions. Five single-mechanism ablations use the same functions.
Ranking quality is measured with graded nDCG@5, Recall@5, and reciprocal rank. The cold-start trace defines no relevance judgments and is excluded, leaving eleven applicable traces. Paired differences carry fixed-seed percentile bootstrap intervals over 10{,}000 resamples and are interpreted descriptively because the scenarios were designed for mechanism coverage and were not sampled from a user population.

The explicit-interest experiment isolates direct correction from behavioral inference. Its frozen fixture contains eight synthetic candidates, two each for attention, quantum computing, robotics, and databases, with publication time held constant. The production ranking function evaluates four successive profiles: attention alone; attention with quantum added; quantum replaced by robotics; and robotics deleted. One record is retained for every candidate and state, including rank, score, reasons, and the presence of the expected topic-match reason. Four transition checks state the expected score direction before analysis. API tests separately replace the stored topic list and request the next recommended digest, while repository tests verify normalization, persistence, and rejection of a digest older than the preference update.

The grounded-assistance harness drives the deployed retrieval and answer pipeline over the fifteen pinned fixtures described under Back-end Development.
Its live flagship run used Claude Opus~4.8 (\nolinkurl{claude-opus-4-8}) with prompt version \texttt{qa-v2}, top-eight retrieval with two context anchors, rerank to four evidence chunks, a 0.25 evidence threshold, a 512-token output cap, and local \texttt{fastembed} embeddings. The 384-dimension vectors are L2-normalized and zero-padded into the 1{,}536-dimension store, which leaves cosine ordering unchanged.
The complete configuration is stored with the evaluation record, and every completion in the reported run was generated live with no cached contribution.

\subsection{UI Testing}

The client's visible-state machinery was exercised in controlled trials that deliver deterministic results to the ViewModel layer and verify the resulting state and disclosure label.
Five content-state conditions each completed 30 of 30 trials with the expected outcome: a live seed transition, a cached warm start, a cached offline disclosure, a cached server-failure disclosure, and an invalid-cache error. The three citation-graph disclosure states (ready, fallback, and empty) likewise each completed 30 of 30 trials, with median transition latencies of 97.11, 103.38, and 66.28~ms respectively.
The trials reached the specified disclosure state in every recorded condition.

Interactive graph behavior was verified by the graph and app-flow suite, which passed 11 of 11 tests, including node selection through the WebView bridge, navigation to a selected paper through the persistent open action, and restoration of the previous selection after returning from paper detail.
Together, these results establish the tested graph presentation, selection, navigation, and restoration behaviors.
The formative five-participant usability study that motivated the graph's redesign is design-stage evidence and is reported in Chapter~3.

The interest editor was exercised as one complete device path. The test edited an existing topic, removed another, added a new topic, saved the profile, navigated away, and returned to the interest screen. The updated topics remained visible after the round trip. Repository tests additionally cover canonical server values, preservation of followed authors, local caching, refresh ordering, and failure without a false local success state.

Provider latency sits on top of this local computation.

Model cost is treated as a first-class performance dimension alongside latency, because a continuously running assistant is constrained as much by provider spend as by response time.
The cost analysis covers the summarization worker, grounded question answering, query embedding, and batched chunk embedding. Recommendation scoring reuses stored vectors and makes no provider call. Unit costs are estimated from provider list prices under the deployed input and output caps.
The estimates assume the deployed caps: summary input bounded at roughly 15{,}000 tokens with a 1{,}024-token output, and question answering built from about six 450-token evidence chunks with a 512-token output.

The results establish the measured behavior of the implemented system across client recovery, graph interaction, preference correction, event synchronization, grounded assistance, and provider routing.
Device measurements use one Android version, device profile, and host; controlled state timings exclude network and frame latency. The behavior-model and explicit-correction evaluations use designed traces and balanced synthetic candidates, while the graded answer-quality evaluation reports one run on each of two provider routes over a fifteen-case corpus. These experiments provide reproducible evidence for the principal mechanisms and identify the areas that require broader device, user, and corpus validation.
